# BCI production integration runbook

This branch adds integrations; it does not deploy BCI or certify a production environment.

## Secrets and keys

Choose one credential provider. `BCI_PENTEST_KMS_KEY_ID` selects AWS KMS envelope encryption using the SDK workload identity chain (`AWS_REGION`, instance/task/web identity). No access key is accepted through the UI. Tenant and purpose are authenticated encryption context. KMS plaintext data keys are zeroed. `node scripts/kms-lifecycle.mjs provision alias/bci-pentest-<deployment>` provisions a dedicated key and enables 90-day rotation. `BCI_KMS_CUSTOM_KEY_STORE_ID` selects an existing AWS CloudHSM custom key store; its rotation requires provisioning a replacement key and rewrapping accounts. KMS-managed keys cannot be exported for local backup. CloudHSM cluster provisioning, backup retention and cluster restore remain operator/provider responsibilities and require live AWS access.

Alternatively set HTTPS `BCI_PENTEST_VAULT_URL`, `BCI_PENTEST_VAULT_TRANSIT_KEY` and workload identity via `BCI_PENTEST_VAULT_ROLE_ID` plus `BCI_PENTEST_VAULT_SECRET_ID_FILE`, or a Vault Agent `BCI_PENTEST_VAULT_TOKEN_FILE`. `NODE_EXTRA_CA_CERTS` supplies a private deployment CA at process startup. AppRole leases are refreshed by reauthentication before expiry. Runtime policy must allow only encrypt/decrypt/rewrap of the designated key. `BCI_PENTEST_VAULT_OPERATOR_TOKEN` is only for operator lifecycle commands, never supplied to API/worker deployments.

`node scripts/vault-lifecycle.mjs provision|status|rotate` controls the Transit key. Operator backup requires `BCI_VAULT_BACKUP_PUBLIC_KEY_FILE` (RSA OAEP SHA-256); restore requires `BCI_VAULT_BACKUP_PRIVATE_KEY_FILE`. `backup <file>` writes AES-GCM encrypted backup material with an RSA-wrapped data key, refuses overwrite and never prints it. Protect the backup file with OS ACLs on Windows (Unix mode 0600 alone is insufficient there). Transit backup requires both exportability and plaintext backup support in Vault 1.21.4. These default to disabled; set BCI_VAULT_ALLOW_TRANSIT_BACKUP=1 only when provisioning a dedicated operator-backup key. Both settings are irreversible; restrict backup/export permissions to separate operators and never grant those paths to runtime identities. `restore <file>` refuses a forced replacement of an existing key. Keep historical key versions until all accounts and backups have been migrated.

## Evidence

Configure Ed25519 signing keys and the historical public-key trust map. `BCI_EVIDENCE_TSA_URL` is an HTTPS RFC3161 authority; `BCI_EVIDENCE_TSA_CA_FILE` is its trusted certificate chain, `BCI_OPENSSL_BIN` chooses OpenSSL. Nonce, certificate chain and message imprint are checked before reporting VERIFIED. `BCI_EVIDENCE_WORM_BUCKET`, `AWS_REGION`, optional `BCI_EVIDENCE_S3_KMS_KEY_ID` and `BCI_EVIDENCE_RETENTION_DAYS` select an Object Lock-enabled, versioned S3 bucket. Archive writes use COMPLIANCE retention, SHA-256 checksum and SSE-KMS; the exact object version's retention is checked. Failures remain FAILED and unconfigured providers remain NOT_CONFIGURED in exported reports. Configure minimum/maximum retention and tenant-prefix restrictions in bucket/IAM policies.

`node scripts/verify-pentest-evidence.mjs report.json <independently-trusted-tail-hash>` verifies exported signatures, ordering and truncation independently of PostgreSQL. Obtain the trusted tail from an independently retained checkpoint, not from the same potentially modified export. `verifyArchivedEvidence` reads the exact locked S3 object version, checks its checksum and signature. A live AWS deletion-denial/retention audit is still required before certifying WORM. The local isolated OpenSSL TSA is a genuine cryptographic test authority, not a commercial external timestamp service.

## Network and discovery

HTTP, native HTTP scanner proxy and gRPC share the pinned engagement address. IPv4 and IPv6 ranges are checked for reserved/private/documentation overlap. Discovery requires the tenant's active APPROVED RESTRICTED scope, exact engagement origin and controlled account. GraphQL introspection, OpenAPI parameters/links and gRPC reflection descriptors produce persisted DISCOVERED_NOT_EXECUTED metadata; they never fabricate fixture object IDs or infer business rules as established facts. Streaming RPC proofs are bounded by message count, aggregate bytes, deadlines and cancellation.

`deploy/worker-network-policy.yaml` denies ingress and all unlisted egress, with narrow PostgreSQL/Vault exceptions. Add approved target/provider IP and port rules through deployment configuration, and use a NetworkPolicy-enforcing CNI. No Internet/DNS exception is included by default. This applies to the whole worker container, including child scanners. Dynamic per-job namespace provisioning and an enforced Kubernetes CNI deployment are not verified by this repository. The Linux CI kernel test verifies actual Docker network namespace denial, not Kubernetes NetworkPolicy enforcement.

## Preparation and rollback

Run migrations 46–48 against a backed-up database, then `node scripts/prepare-trivy-db.mjs` before scanner jobs. The DB preparation budget is separate from scan time; a verified parallel OCI range fallback handles slow clients. Only fresh v2 cache metadata counts as prepared. Preserve the writable cache volume across worker replacements. Worker image includes Chromium, OpenSSL, pinned scanners and a database heartbeat healthcheck for its own worker IDs. Mount writable temporary/cache directories when using a read-only root filesystem, drop unnecessary capabilities and apply no-new-privileges. Naabu privileges must be explicitly chosen for the intended scan mode.

Run `node scripts/preflight.mjs` with production secrets mounted. Missing migration, external credential provider, signing/trust map, anchor configuration, scanner or actual Chromium launch fails readiness. This command does not prove external WORM retention or kernel policy enforcement: perform those service/deployment audits separately. Never upload operator keys, Vault logs or backups as CI artifacts.

Rollback: stop accepting new jobs, cancel/drain active jobs and perform configured fixture cleanup; restore the previous immutable worker/API image. These migrations are additive and the old image can leave their tables/columns in place. Do not drop evidence or roll back rotated encryption keys. Restore PostgreSQL into an empty isolated database using the existing backup/restore scripts and validate signatures/provider decryptability before cutover. No production rollback, backup restore or deployment was performed by this development task.
